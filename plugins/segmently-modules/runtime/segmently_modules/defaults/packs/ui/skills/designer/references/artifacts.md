# artifacts: the brief, the audit and the review

Steps 5–7 of `designer`. Every artifact lives in `<artifacts>/<feature>/` (`[ui] artifacts`,
default `.design`; the feature: short, lowercase, hyphenated). Tracked in git: the brief, the
audit, the review and `mockups/*.html`. Not tracked: `screenshots/` — evidence, regenerated by
running the step again (keep the folder out of git, and never write a screenshot next to the
brief).

```
<artifacts>/<feature>/
├── AS_IS_AUDIT.md        # rework track only
├── DESIGN_BRIEF.md       # the prototype's output
├── mockups/<screen>-<state>.html
├── screenshots/          # mock-*.png, review-*.png — not tracked
└── DESIGN_REVIEW.md      # the review's output
```

## DESIGN_BRIEF.md

```markdown
# Design Brief: <feature name>

- **Feature:** <feature> · **Track:** new | rework (→ AS_IS_AUDIT.md) · **Date:** <YYYY-MM-DD>
- **Surface kind:** <kind> (a task over two kinds: which surface is which)
- **Modules involved:** <the modules step 3 found>

## Problem
The friction from the user's side, not technical, not metrics. Rework: the audited dead ends
(D#, F#) this redesign removes.

## Flow patterns applied
Which of FP-1…FP-11 shape the flow; rework: which dead end each resolves ("FP-3 page + side
panel → removes D2").

## Solution
What the interface does about it, described as an experience, not a feature list.

## Experience principles
At most three, each resolving a tension: <principle> — <what it means in practice>.

## Existing patterns
The UX invariants in force, the compositions in use, the catalogue entries to follow — with the
designer doc each came from.

## Component inventory
| Component | Exists / Modify / New | Source, notes |
"New" needs one line on why no shared component covers it.

## Key interactions
What the user does → what the interface does: state changes, transitions, feedback.

## States covered
Which of default / loading / empty / error / success the surface has, and the mock showing each.

## Responsive behaviour
How the layout adapts across `[ui] sizes`; the components that change behaviour, not only size.

## Mockups
| File | Shows |
| mockups/<screen>-<state>.html | <what> |
| mockups/<screen>-<state>-v<N>-<axis>.html | variant N — its thesis and axis |
| screenshots/mock-<screen>-<size>.png | the capture |

## Checker self-check
<N> findings → fixed: <rules>; left: <rule — why>; blocking class **clear**.

## Out of scope
What this does not cover — it prevents scope creep in the build and the review.

## Open questions
The unresolved decisions with your recommended answers; empty after the approval.
```

## AS_IS_AUDIT.md

```markdown
# As-is Audit: <feature name>

## Path trace           — the click tree and the metrics table against the budget
## Dead ends            — | # | Dead end or friction | Where | Severity | Breaks |
## Preserve list        — what must survive the redesign
## Mapping              — | Today | Target | Reuse |
## Output findings      — F# with severity, owner and the phase that fixes it (when step E ran)
```

## DESIGN_REVIEW.md

```markdown
# Design Review: <feature name>

- **Reviewed against:** DESIGN_BRIEF.md (<date>) | no brief (an existing surface)
- **Designer docs checked:** <the docs step 4 loaded>
- **Review tier:** 1 checker only | 2 checklist + checker | 3 two-reviewer critique + checklist (<why>)
- **Date:** <YYYY-MM-DD> · **Verdict:** PASS | BLOCKED: <N> must-fix (degraded — no screenshots, when so)

## Screenshots captured
| Screenshot | Size | Theme | Shows |

## Summary
Two or three sentences: the overall quality and the biggest finding.

## Invariant check
| # | Invariant (module) | Verdict: kept / broken → Must fix #N |

## Evidence
- Checker: <N> findings — <rule = count, …>; blocking class: clear | <list>. (No checker named: say so.)
- Rendered (<size>, <theme>): smallest text <px> at contrast <x:1>; widest table <visible %>; console errors <N>.
- Tier 3: reviewers A and B isolated | degraded (one context); the synthesis in one line.

## Must fix
1. **<issue>** — <component and file>. See `screenshots/<file>.png`. _Fix: <suggestion>._

## Should fix
## Could improve
## What works well
Candidates for the module's designer doc (visual patterns, anti-patterns).

## Waivers
<a Must fix the user waived in writing, and the reason> (omit when none)

## Follow-ups
- [ ] Move finding #N into the module's designer doc (anti-patterns)
- [ ] A new pattern from this feature → the team's component catalogue
```

A re-review appends `## Re-review <date>` to the same file: the affected screenshots captured
again, the affected categories run again, the new verdict.
